# Hero Defense fresh-start Functions candidate

Deployed disabled; production gameplay verification remains pending. This source replaces the new site's pending direct-Firestore profile with a gated Functions profile. It does not change the existing Sites Worker, old Git repository/Pages/stag, or any production data.

`gameApi` is a Firebase Functions v2 HTTP function. The browser uses Firebase Auth and sends its ID token to the API. `server/http.mjs` checks audience, issuer, expiry and verifies the token/account with Firebase Auth. Ownership, administrator checks, transactions, CAS, server reward calculation and receipt retry logic reuse the existing game server. Runtime Google auth uses metadata credentials, never a key file or browser session.

All game storage is pinned to `projects/hero-defense-3d-independent/databases/(default)/documents/hd3d_live_server/state/{hd3d_table}/{rowId}`. No request can choose a namespace. Old root collections and the abandoned `hd3d_live` direct namespace are neither imported nor queried. The same Firebase UID starts a fresh game here. Browser keys remain the new `hd3d_live` keys, separated from old stag. Git Pages shares an origin across paths, so CORS cannot isolate repositories; ID-token/ownership validation is essential.

`server/live.mjs` is disabled unless `HD3D_LIVE_ENABLED=true`. The client is disabled until `functionsActivation` is `deployment-verified` and `apiUrl` is the verified deployment endpoint. Default `apiUrl` is empty and there is no Sites fallback. Do not activate based on an inferred URL. Production accepts the `https://hyunjk11.github.io` browser origin. Local QA explicitly uses the demo Auth project and a loopback-only RAM transport; this is not production Functions/Firestore verification.

The create-only `initialOwnerPlan` requires independently verified UID/email for the approved owner. It never promotes an account on login. The approved owner document has been created and reloaded through the official console in the new namespace. No other initial catalogue documents are required. Server definitions are bundled code; the old direct catalogue/activation documents are not needed.

Run `node scripts/stage-functions.mjs` from the candidate root. It stages the exact 58-module dependency closure and hashes. `firebase.json` deploys only this Functions codebase, never Rules, Auth or Hosting. QA scripts/accounts, real saves and node_modules are excluded. Preserve `.npmrc` and the dependency lockfile. All tests must match this staged manifest before deployment.

Proposed resources: Node 22, asia-northeast3, 256 MiB/1 CPU, concurrency 8, minInstances 0, maxInstances 1, timeout 180 seconds. The public HTTP transport still requires application authentication for data. minInstances 0 permits cold starts; maxInstances is not a spending cap. Blaze, Cloud Functions/Cloud Run/Cloud Build/Artifact Registry readiness, deployer permissions and runtime datastore access require review. Required APIs and the first disabled Functions deployment are confirmed; no broader IAM grant was introduced by this release. Runtime game API verification remains pending. The proposed existing service account must be verified; do not create keys or broaden roles automatically.

Economy authority: `server/economy.mjs` is installed only by the new Functions handler. Generic progress saves accept cosmetic preferences and independently priced training increments (including debounced batches), never arbitrary currency, inventory, codex, stage or research transitions. New accounts start empty; guest balances are not imported. Gear/town actions, mail, normal/challenge settlement run in server transactions with owned receipts. Prices, caps, draws, item identities and grants are computed on the server. Hard/dungeon server rewards and first-clear/target/extra-chest policies are unchanged. The browser does not announce a locally guessed boss-item grade in Functions account mode; authoritative loot appears in the existing result/chest UI.

Remaining trust boundary: the server checks owned run, mode, unlocks, elapsed time, bounded waves/kills and idempotence. It does not simulate combat. A modified client can still fabricate plausible combat progress or stars within those bounds. This is different from freely overwriting save balances or choosing legendary results, which the new tests reject. Generic growth caches are ignored; the separate server growth wallet is authoritative. Existing Worker APIs are preserved for the protected old service and are not this candidate's live entry point.

Independent boundary fixes: mail that exceeds a canonical currency/material/medal cap is deferred as a whole without consuming its entitlement or applying its items/ownership. Generated reward identities are checked against existing items and other new rewards before commit, including items that addChests classified as automatic dismantles. Identity collisions abort the complete transaction instead of losing a chest. Settlement accepts the same 8–80 character token contract as growth start/progress.

Consumable gear/town operations also reject balance truncation atomically: the item, chest, price and receipt remain unchanged at the cap, and a confirmed failure lets the existing client release its purchase guard. The older combat reward cap policy and 64 KiB generic save limit are unchanged limitations, not solved by this patch.

Deployment order after cost/service review: inventory the target function and IAM without bypassing prior denials; deploy disabled; verify returned revision/URL and namespace routing; verify owner UID and apply only the create-only plan; enable runtime and perform approved new-namespace QA; activate the static client only after endpoint/readback checks. Publish the new repository/site separately. Preserve existing repository/main/Pages/stag. Rollback by disabling the new endpoint and reverting the new static build, retaining new receipts/data; never redirect new saves to the old Worker or delete old/new data as rollback.
